# router-1c-mcp

MCP-сервер на Rust: один процесс обслуживает несколько баз 1С и пересылает
JSON-RPC в их опубликованные HTTP-сервисы. База выбирается обязательным
параметром `base`, имя MCP-сервера — `router-1c-mcp`.

Инструменты живут не в роутере, а в расширении `MCP_Сервер` Владимира
Харина — <https://github.com/vladimir-kharin/1c_mcp> (MIT). Роутер их
только пересылает: без расширения на базе ему нечего отдавать.

Публичная история начинается с версии 0.8.0. Установка — пошагово в
[INSTALL.md](INSTALL.md), что изменилось — в [CHANGELOG.md](CHANGELOG.md).

## Как работает

- `POST /mcp` — rmcp StreamableHTTP, stateless: `Mcp-Session-Id` игнорируется,
  после перезапуска роутера клиенту не нужно новое рукопожатие.
- При старте состав инструментов собирается **со всех баз сразу**: каждая база
  опрашивается параллельно (`initialize` → версия расширения, затем
  `tools/list`) в отдельной Tokio-задаче, роутер дожидается ответа всех задач.
  Недоступная база не мешает остальным и не обрывает опрос.
- Инструменты объединяются по имени. У каждого инструмента в параметре `base`
  свой узкий `enum`: только те базы, которые этот инструмент реально отдают.
  Остальные параметры и `required` инструмента сохраняются.
- Если одно и то же имя пришло с нескольких баз, берётся определение с **самой
  старой версией расширения** (числовое сравнение по компонентам, включая
  четвёртый; при равенстве — порядок баз в настройках). Расхождение схем
  пишется в журнал с именами баз, версиями и выбранным источником. Версия,
  которую нельзя сравнить, расценивается как неудачный опрос базы — причина в журнале.
- Вызов пересылается в `{url}/hs/{service_root}/rpc` выбранной базы с Basic Auth
  (`username`/`password` из списка баз).
- Роутер сам проверяет матрицу «инструмент → базы» на каждом вызове. Если
  инструмент не предоставляется выбранной базой, вызов отбивается до сети:
  клиент получает `isError` с русским текстом ошибки единого вида —
  «Инструмент 'X' недоступен для базы 'Y'. Допустимые базы: [...]». Если имени
  нет в составе вообще, текст другой: «Инструмент 'X' отсутствует в составе
  инструментов (допустимые: [...])». Запрос в базу в обоих случаях не уходит.
  Порядок проверок: белый список → матрица → пересылка вызова в базу.
- `GET /health` — служебная проверка без рукопожатия MCP.
- `GET /download/{base}?kind=..&id=..` — скачивание артефактов через роутер,
  `POST /upload/{base}?kind=..&id=..` — загрузка.

## Файл состава инструментов

Состав пишется в JSON-файл при каждом старте (матрица и файл строятся по
полному набору инструментов, до применения белого списка):

```json
{
  "_generated": "2026-10-28T07:06:53Z",
  "tools_enabled": ["execute_query", "db_tables"],
  "common": ["execute_query", "db_tables"],
  "separate": {
    "base-a": ["list_artifacts"],
    "base-b": ["export_artifact"]
  }
}
```

- `_generated` — момент сборки в UTC (ISO-8601, суффикс `Z`);
- `tools_enabled` — белый список инструментов. Секция **только читается** и
  переписывается без изменений: список из файла — ручная настройка, значение
  `MCP_TOOLS_ENABLED` в файл не попадает. Если списка в файле не было, ключа в
  новом файле тоже не будет;
- `common` — инструменты, которые есть на всех опрошенных базах;
- `separate` — только «свои» инструменты базы, вне `common` (пустые записи не
  пишутся);
- версии расширений в файл не попадают — они остаются в журнале.

Порядок ключей в файле строгий: `_generated`, затем `tools_enabled` (если он
есть), затем `common`, затем `separate`. Порядок обеспечивает сериализация через
структуру с полями в этом порядке — обычный JSON-объект ключи сортирует.

Файл всегда перезаписывается целиком: состав с пустым набором тоже заменяет
файл (например, когда не ответила ни одна база). Единственное, что переносится
из прежнего файла в новый, — секция `tools_enabled`. Путь выбирается так:

| Что задано | Куда пишется состав |
| --- | --- |
| `MCP_TOOLS_FILE` (непустой) | по указанному пути |
| `MCP_ONEC_BASES_FILE` | `tools.json` рядом с файлом баз |
| только `MCP_ONEC_BASES` (inline) | `tools.json` в рабочем каталоге |

Относительные пути отсчитываются от рабочего каталога. Если при старте файл
записать не удалось, роутер завершает запуск с понятной ошибкой.

## Белый список инструментов

Источники — `MCP_TOOLS_ENABLED` (имена через запятую) и секция `tools_enabled`
в файле состава. Непустая переменная главнее файла; значение из переменной в
файл не пишется. Список глобальный: он одинаково применяется к выдаче
`tools/list` и к вызову инструмента, поэтому отключённый инструмент не вызвать,
даже зная его имя. Файл состава при этом остаётся полным — белый список его не
сужает и на `common`/`separate` не влияет.

Файл баз (`MCP_ONEC_BASES_FILE` или `MCP_ONEC_BASES`) описывает подключения:
имена, адреса, учётные данные, `service_root`, `max_concurrent`. В обёрнутом
виде (`{"bases": [...], "retry_attempts": N}`) допускается ещё поле
`retry_attempts` — сколько раз повторять опрос. Поле `tools_enabled` в файле
баз больше не читается — если оно там осталось, оно игнорируется, а список
надо перенести в файл состава или в переменную.

## Восстановление недоступных баз

Раз в две минуты роутер параллельно опрашивает только те базы, по которым
ещё нет успешного снимка. Повторов конечное число: по умолчанию пять попыток
(десять минут), дальше цикл останавливается — бесконечно базы не
опрашиваются. Если ответили все базы, повтор прекращается досрочно. Число
попыток задаётся переменной `MCP_RETRY_ATTEMPTS` (главнее) или полем
`retry_attempts` в обёрнутом файле баз; `0` выключает повтор.

Базы с успешным снимком повторно не опрашиваются, а сами снимки не удаляются:
если база потом исчезнет, её инструменты останутся в списке, а ошибка
возникнет при обычной пересылке вызова.

Когда база восстановилась, её снимок сохраняется, весь состав пересобирается,
файл состава перезаписывается (секция `tools_enabled` сохраняется как была), а
инструменты публикуются в работающий сервер
(`replace_tools`) — перезапуск не нужен. Публикация выполняется только после
успешной записи файла; при ошибке записи она повторяется на следующем тике.
Фоновая задача останавливается вместе с сервером.

Новый список инструментов клиент увидит после переподключения: `listChanged`
роутер не заявляет и уведомлений не рассылает.

## Для разработки

Пользователю сборка не нужна: готовые архивы — в
[Releases](https://github.com/Regsorm/router-1c-mcp/releases). Из исходников:

```
cd rust
cargo build --release
```

Linux — кросс-сборкой: `cargo zigbuild --release --target
x86_64-unknown-linux-gnu.2.17` (glibc не новее 2.17) или
`x86_64-unknown-linux-musl` (статический бинарь); нужен zig 0.16+.

Настройка — только переменными окружения, файла конфигурации нет; список
переменных — в [.env.example](.env.example).

## Расширение 1С

Инструменты живут не в роутере, а в расширении `MCP_Сервер` для 1С (чужое, MIT):
<https://github.com/vladimir-kharin/1c_mcp>. Роутер инструменты не реализует —
только пересылает вызовы в опубликованные HTTP-сервисы баз.
